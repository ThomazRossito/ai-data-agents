## 1. Tipos Problemáticos (sem mapeamento trivial)

| SQL Server | Databricks | Problema | Ação |
|---|---|---|---|
| `TINYINT` | **`SMALLINT`** (não `TINYINT`) | SQL Server `TINYINT` é `0-255` (unsigned); Databricks `TINYINT` é signed `-128..127` | Usar `SMALLINT` para preservar o range completo. **Corrige `kb/migration/index.md`**, que hoje lista `TINYINT`→`TINYINT` como mapeamento direto — isso trunca/erra qualquer valor de origem > 127 |
| `MONEY` / `SMALLMONEY` | `DECIMAL(19,4)` / `DECIMAL(10,4)` | `MONEY` é fixed-point de 8 bytes, 4 casas decimais | Nunca usar `FLOAT`/`DOUBLE` para valores monetários (anti-padrão M01 em `kb/migration/index.md`) |
| `UNIQUEIDENTIFIER` | `STRING` | Sem tipo UUID nativo | Armazenar como string de 36 caracteres; gerar novos valores com `uuid()` |
| `HIERARCHYID` | `STRING` | Sem tipo hierárquico nativo | Serializar para representação em string; reimplementar travessia de hierarquia com CTE recursiva |
| `GEOGRAPHY` / `GEOMETRY` | `STRING` (WKT/GeoJSON) | Sem tipo espacial nativo | Armazenar como string WKT ou GeoJSON; usar funções **H3** do Databricks para operações geoespaciais |
| `ROWVERSION` / `TIMESTAMP` (nome legado SQL Server) | Dropar ou `BIGINT` | **Não é uma data** — é contador de versionamento de linha | Dropar a coluna, ou converter para `BIGINT` se usada para controle de concorrência |
| `SQL_VARIANT` | `STRING` ou `VARIANT` | Tipo dinâmico sem equivalente direto | Inspecionar o uso real dos dados; escolher tipo específico baseado no conteúdo observado |
| `XML` | `STRING` | Sem tipo XML nativo | Armazenar como string; parsear com funções XPath quando necessário |
| `DATETIMEOFFSET` | `STRING` ou `TIMESTAMP` + coluna de offset separada | Sem timestamp timezone-aware nativo | Se o offset importa para a regra de negócio, separar em duas colunas e documentar a estratégia |
| `TIME` | `STRING` | Sem tipo `TIME` nativo | Armazenar como string `'HH:MM:SS'` |
| `IMAGE` / `NTEXT` / `TEXT` | `BINARY` / `STRING` | Tipos SQL Server depreciados | Converter para `BINARY` (binário) ou `STRING` (texto) conforme o conteúdo |

> **Nota de reconciliação com `kb/migration/index.md`:** a tabela de tipos existente também
> lista `IDENTITY` como "sem equivalente — documentar como surrogate key". Isso está incompleto:
> Databricks suporta `GENERATED ALWAYS/BY DEFAULT AS IDENTITY` nativamente (ver seção 2.1).
> Use este arquivo como fonte de verdade para os dois casos (`TINYINT` e `IDENTITY`) até a
> próxima atualização do índice de migração.

## 2. DDL — Constructs SQL Server sem Equivalente Direto

### 2.1 IDENTITY — carga inicial vs regime permanente

```sql
-- Fase 1 — carga inicial: permite inserir valores de chave já existentes na origem
CREATE TABLE IF NOT EXISTS migration_catalog.adventureworks_bronze.DimProduct (
    ProductKey          BIGINT GENERATED BY DEFAULT AS IDENTITY,
    ProductAlternateKey STRING NOT NULL,
    ...
)
COMMENT 'Migrated from AdventureWorksDW.dbo.DimProduct';
```

- **`GENERATED BY DEFAULT AS IDENTITY`** — Databricks atribui um valor apenas se nenhum for
  fornecido. Usar durante a migração de dados que já possuem valores de chave.
- **`GENERATED ALWAYS AS IDENTITY`** — Databricks sempre atribui o valor; `INSERT`s que
  especificam um valor para a coluna falham. Trocar para este modo **após** a carga inicial,
  quando linhas novas devem receber chaves geradas pelo sistema.

Cite: `3.1 Lecture - Schema and DDL Conversion.md`, seção "IDENTITY Columns".

### 2.2 PRIMARY KEY / FOREIGN KEY / UNIQUE — informational + RELY + expectations

SQL Server aplica (`enforce`) essas constraints em tempo de escrita. Databricks as trata como
**metadata informacional apenas** — não há enforcement de PK/FK/UNIQUE.

| Constraint | SQL Server | Databricks |
|---|---|---|
| `PRIMARY KEY` | Enforced (cria índice clustered) | Informational — adicionar `RELY` para o otimizador usar em join elimination |
| `UNIQUE` | Enforced (índice único) | Informational via PK; aplicar de fato via **Lakeflow Declarative Pipelines expectations** |
| `FOREIGN KEY` | Enforced (integridade referencial) | Informational, não aplicado |
| `NOT NULL` | Enforced | Enforced (idêntico) |
| `CHECK` | Enforced | Enforced (idêntico) |
| `DEFAULT` | Aplicado no insert | Aplicado no insert (idêntico) |

```sql
-- RELY habilita o otimizador a usar a PK para otimizações mesmo sem enforcement físico
CONSTRAINT pk_dim_product PRIMARY KEY (productkey) RELY
```

Para qualidade de dados de fato aplicada (já que PK/UNIQUE não têm enforcement), usar
expectations do Lakeflow Declarative Pipelines na ingestão: `@dp.expect_or_fail`,
`@dp.expect_or_drop`, ou `@dp.expect` para validar unicidade e demais regras.

Cite: `3.1 Lecture - Schema and DDL Conversion.md`, seção "Constraint Behavior Differences".

### 2.3 Computed Columns

| SQL Server | Databricks |
|---|---|
| `[Margin] AS ([SalesAmount] - [TotalProductCost])` | `margin GENERATED ALWAYS AS (sales_amount - total_product_cost)` |
| `[Margin] AS (...) PERSISTED` | `margin GENERATED ALWAYS AS (...)` — Databricks sempre armazena fisicamente (`PERSISTED` é o único comportamento) |

### 2.4 Dropar: COLLATE, Filegroups, Session Settings

| Clause SQL Server | Ação Databricks |
|---|---|
| `COLLATE SQL_Latin1_General_CP1_CI_AS` | Dropar — `STRING` é sempre UTF-8; case-insensitive vira `LOWER()`/`UPPER()` na query |
| `ON [PRIMARY]` / `TEXTIMAGE_ON [PRIMARY]` | Dropar — Delta Lake gerencia armazenamento automaticamente |
| `INCLUDE (col1, col2)` em índices | Dropar — sem covering index no Delta |
| `WITH (PAD_INDEX = ON, FILLFACTOR = 80)` | Dropar — sem fill factor |
| `SET ANSI_NULLS ON` / `SET QUOTED_IDENTIFIER ON` | Dropar — session settings do SQL Server, sem efeito no Databricks |

### 2.5 Clustered Index → CLUSTER BY (Liquid Clustering)

```sql
-- SQL Server: clustered index em (OrderDateKey, ProductKey)
-- Databricks:
CLUSTER BY (order_date_key, product_key)
```

- **Non-clustered indexes**: sem equivalente — Delta usa file-level statistics e data skipping.
- **`CHANGE_TRACKING` / CDC** → `delta.enableChangeDataFeed = true`.
- **`DATA_COMPRESSION = PAGE`** → automático (compressão colunar Parquet).
- Partition scheme/function do SQL Server → `PARTITIONED BY` (usar com moderação; Liquid
  Clustering é preferível para a maioria dos workloads).

### 2.6 Indexed View → Materialized View / Lakeflow Declarative Pipelines

| SQL Server | Databricks | Uso |
|---|---|---|
| Indexed View (single-table, auto-mantida) | SQL Materialized View | BI dashboards, auto-refresh on query |
| Indexed View (query complexa, workarounds em camadas) | Lakeflow Declarative Pipelines Materialized View | Multi-table joins, window functions, refresh agendado |

SQL Server indexed views são restritas: single table (sem joins), sem window functions, sem
`HAVING`/`ORDER BY`/`LIMIT`, agregados limitados (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`), apenas
funções determinísticas, sem `DISTINCT` em agregados. Databricks Materialized Views suportam
joins multi-tabela e window functions — views SQL Server em camadas (layered views) frequentemente
se consolidam em uma única MV Databricks.

**Atenção:** Materialized Views SQL requerem SQL Warehouse Serverless ou Pro. Para compute
geral, usar Lakeflow Declarative Pipelines.

Cite: `3.1 Lecture - Schema and DDL Conversion.md`, seções "Table Properties and Optimization"
e "Indexed Views to Materialized Views".

## 3. Catálogo de Funções

### 3.1 Data/Hora (complementa `dialect-concepts.md`)

| T-SQL | Databricks SQL | Nota |
|---|---|---|
| `GETDATE()` | `CURRENT_TIMESTAMP()` | |
| `SYSDATETIME()` | `CURRENT_TIMESTAMP()` | Variante de alta precisão mapeia para a mesma função |
| `GETUTCDATE()` | `UTC_TIMESTAMP()` | |
| `EOMONTH(col)` | `LAST_DAY(col)` | Fim do mês |
| `ISDATE(col)` | `TRY_CAST(col AS DATE) IS NOT NULL` | Sem equivalente direto |
| `SWITCHOFFSET(col, tz)` | `FROM_UTC_TIMESTAMP(col, tz)` | Conversão de timezone |
| `TODATETIMEOFFSET(col, tz)` | `TO_UTC_TIMESTAMP(col, tz)` | Atribuição de offset de timezone |

### 3.2 CONVERT — Style Codes → Format Strings

`CONVERT` não existe no Databricks; usar `CAST` (ANSI) ou funções de formatação de data.

| Style | T-SQL | Databricks SQL |
|---|---|---|
| 101 | `CONVERT(VARCHAR, col, 101)` | `DATE_FORMAT(col, 'MM/dd/yyyy')` |
| 103 | `CONVERT(VARCHAR, col, 103)` | `DATE_FORMAT(col, 'dd/MM/yyyy')` |
| 104 | `CONVERT(VARCHAR, col, 104)` | `DATE_FORMAT(col, 'dd.MM.yyyy')` |
| 108 | `CONVERT(VARCHAR, col, 108)` | `DATE_FORMAT(col, 'HH:mm:ss')` |
| 112 | `CONVERT(VARCHAR, col, 112)` | `DATE_FORMAT(col, 'yyyyMMdd')` |
| 120 | `CONVERT(VARCHAR, col, 120)` | `DATE_FORMAT(col, 'yyyy-MM-dd HH:mm:ss')` |
| 126 | `CONVERT(VARCHAR, col, 126)` | `DATE_FORMAT(col, "yyyy-MM-dd'T'HH:mm:ss")` |

Regra geral: `CONVERT(type, x)` sem style code → `CAST(x AS type)`. `TRY_CONVERT(type, x)` →
`TRY_CAST(x AS type)`. `TRY_PARSE(x AS DATE USING 'en-US')` → `TRY_TO_TIMESTAMP(x, 'MM/dd/yyyy')`
(parsing culture-specific). `STR(x)` → `CAST(x AS STRING)` (note: `STR` tem right-padding em T-SQL, `CAST` não).

Cite: `3.4 Lecture - SQL and Code Conversion.md`, seções "Type Casting and NULL Handling" e
"Common CONVERT Style Code Reference".

### 3.3 String Functions (complementa `dialect-concepts.md`)

| T-SQL | Databricks SQL | Nota |
|---|---|---|
| `CHARINDEX('x', col)` | `INSTR(col, 'x')` | **Ordem dos argumentos invertida** — `CHARINDEX(busca, alvo)` vs `INSTR(alvo, busca)` |
| `STUFF(col, start, len, repl)` | `CONCAT(LEFT(col, start-1), repl, SUBSTRING(col, start+len))` | Sem equivalente direto — compor com funções de string |
| `LEN(col)` | `LENGTH(col)` | T-SQL `LEN` exclui espaços à direita; `LENGTH` não |
| `DATALENGTH(col)` | `OCTET_LENGTH(col)` | Tamanho em bytes |
| `PATINDEX('%pattern%', col)` | `REGEXP_INSTR(col, 'pattern')` | Baseado em regex no Databricks |
| `REPLICATE(col, n)` | `REPEAT(col, n)` | Renomeado |
| `STRING_AGG(col, sep) WITHIN GROUP (ORDER BY ...)` | `ARRAY_JOIN(SORT_ARRAY(COLLECT_LIST(col)), sep)` | Collect → sort → join. Sem o `SORT_ARRAY`, a ordem não é garantida |
| `STRING_SPLIT(col, sep)` | `SPLIT(col, sep)` | Retorna array no Databricks |

### 3.4 NULL Handling e Condicionais

| T-SQL | Databricks SQL | Nota |
|---|---|---|
| `ISNULL(x, y)` | `COALESCE(x, y)` ou `NVL(x, y)` | `NVL` é alias específico do Databricks |
| `IIF(cond, t, f)` | `IF(cond, t, f)` | `IIF` não é suportado no Databricks |
| `CHOOSE(idx, v1, v2, ...)` | `ELEMENT_AT(ARRAY(v1, v2, ...), idx)` | |

### 3.5 Matemática e Sistema

| T-SQL | Databricks SQL | Nota |
|---|---|---|
| `SQUARE(x)` | `POWER(x, 2)` | |
| `LOG(x)` | `LN(x)` | T-SQL `LOG(x)` de 1 argumento é log natural |
| `ATN2(y, x)` | `ATAN2(y, x)` | |
| `CEILING(x)` | `CEIL(x)` | |
| `NEWID()` | `UUID()` | |
| `COUNT_BIG(*)` | `COUNT(*)` | Databricks retorna `BIGINT` por padrão |
| `@@ROWCOUNT` | `ROW_COUNT()` | Disponível em SQL Scripting |
| `SUSER_SNAME()` | `CURRENT_USER()` | |
| `DB_NAME()` | `CURRENT_CATALOG()` | |
| `SCHEMA_NAME()` | `CURRENT_SCHEMA()` | |
| `ISNUMERIC(x)` | `TRY_CAST(x AS DOUBLE) IS NOT NULL` | |

### 3.6 JSON

| T-SQL | Databricks SQL | Nota |
|---|---|---|
| `JSON_VALUE(col, '$.key')` | `col:key` (dot notation) ou `GET_JSON_OBJECT(col, '$.key')` | |
| `JSON_QUERY(col, '$.arr')` | `col:arr` ou `FROM_JSON(col, schema)` | |
| `ISJSON(col)` | `TRY_FROM_JSON(col, schema) IS NOT NULL` | |
| `JSON_MODIFY(col, path, val)` | Sem equivalente direto | Reconstruir com `TO_JSON` |

### 3.7 TOP → LIMIT

```sql
-- T-SQL
SELECT TOP 10 SalesOrderID, TotalDue FROM Sales.SalesOrderHeader ORDER BY TotalDue DESC;

-- Databricks
SELECT SalesOrderId, TotalDue
FROM migration_catalog.adventureworks_bronze.salesorderheader
ORDER BY TotalDue DESC
LIMIT 10;
```

`TOP N WITH TIES` **não tem equivalente direto** — substituir por window function e filtrar:

```sql
SELECT sales_order_id, total_due
FROM (
    SELECT SalesOrderId, TotalDue, RANK() OVER (ORDER BY TotalDue DESC) AS rnk
    FROM migration_catalog.adventureworks_bronze.salesorderheader
)
WHERE rnk <= 10;
```

### 3.8 PIVOT sem colchetes

```sql
-- T-SQL: IN clause usa colchetes
PIVOT ( SUM(TotalDue) FOR OrderYear IN ([2011], [2012], [2013], [2014]) ) AS pvt;

-- Databricks: valores sem colchetes, sem alias obrigatório na subquery de PIVOT
PIVOT ( SUM(TotalDue) FOR OrderYear IN (2011, 2012, 2013, 2014) );
```

### 3.9 CROSS/OUTER APPLY → LATERAL

| T-SQL | Databricks SQL |
|---|---|
| `CROSS APPLY (...)` | `JOIN LATERAL (...)` |
| `OUTER APPLY (...)` | `LEFT JOIN LATERAL (...)` — preserva linhas sem correspondência |

```sql
-- OUTER APPLY -> LEFT JOIN LATERAL (top 3 pedidos por cliente, preservando clientes sem pedidos)
SELECT c.CustomerId, c.FirstName, o.SalesOrderId, o.TotalDue
FROM migration_catalog.adventureworks_bronze.customer c
LEFT JOIN LATERAL (
    SELECT SalesOrderId, TotalDue
    FROM migration_catalog.adventureworks_bronze.salesorderheader h
    WHERE h.CustomerId = c.CustomerId
    ORDER BY TotalDue DESC
    LIMIT 3
) o;
```

### 3.10 FOR XML / FOR JSON

| T-SQL | Databricks SQL |
|---|---|
| `FOR JSON PATH` | `TO_JSON(COLLECT_LIST(STRUCT(col1, col2, ...)))` |
| `FOR XML PATH('')` (padrão de lista separada por vírgula via `STUFF`) | `ARRAY_JOIN(COLLECT_LIST(col), ', ')` |

Cite: `3.4 Lecture - SQL and Code Conversion.md`, seções 2 a 8 (Date/Time, String, Type
Casting/NULL, PIVOT/UNPIVOT, TOP vs LIMIT, APPLY Operators, FOR XML/JSON).

## 4. Stored Procedures → SQL Scripting ou Python

Databricks Runtime 16.0+ suporta **SQL Scripting**: `DECLARE`, `IF`/`ELSE`, `WHILE`, `FOR`,
`CASE`, e tratamento de exceções (`EXCEPTION`) dentro de um corpo de procedure SQL. Isso cobre a
maioria dos padrões de stored procedure T-SQL.

**Critério de decisão:**
- **SQL Scripting** — corpo é primariamente `SELECT`/DML com controle de fluxo simples.
- **Python notebook** — a procedure tem cursor loops, dynamic SQL, chamadas a serviços
  externos, ou lógica CLR.

```sql
-- Databricks SQL Scripting (DBR 16+) — equivalente à stored procedure T-SQL usp_GetCustomerOrders
CREATE OR REPLACE PROCEDURE migration_catalog.adventureworks_bronze.get_customer_orders(
    CustomerId INT,
    StartDate  DATE DEFAULT NULL,
    EndDate    DATE DEFAULT NULL
)
RETURNS TABLE (
    sales_order_id BIGINT,
    order_date     TIMESTAMP,
    total_due      DECIMAL(19,4),
    customer_name  STRING
)
LANGUAGE SQL
AS $$
  SELECT
    o.SalesOrderId AS sales_order_id,
    o.OrderDate AS order_date,
    o.TotalDue AS total_due,
    CONCAT(c.FirstName, ' ', c.LastName) AS customer_name
  FROM migration_catalog.adventureworks_bronze.salesorderheader o
  JOIN migration_catalog.adventureworks_bronze.customer cu ON o.CustomerId = cu.CustomerId
  JOIN migration_catalog.adventureworks_bronze.person   c  ON cu.PersonId  = c.BusinessEntityId
  WHERE o.CustomerId = CustomerId
    AND (StartDate IS NULL OR o.OrderDate >= StartDate)
    AND (EndDate   IS NULL OR o.OrderDate <= EndDate)
  ORDER BY o.OrderDate DESC;
$$;
```

**Diferenças-chave em relação ao T-SQL:**
- `@Parametro` → parâmetro nomeado sem o prefixo `@`
- `= NULL` (parâmetro opcional) → `DEFAULT NULL`
- `SET NOCOUNT ON` não tem equivalente — omitir
- Concatenação de string usa `CONCAT()` em vez de `+`
- Corpo da procedure é delimitado por `$$`

Cite: `3.4 Lecture - SQL and Code Conversion.md`, seção "Stored Procedure Conversion".

## 5. Cursors — Sempre Set-Based (nunca 1:1)

**Regra invariável:** cursores nunca devem ser reproduzidos linha-a-linha no Databricks.
Lakebridge detecta blocos `CURSOR` e emite um warning, mas **não converte automaticamente** —
a lógica dentro do loop precisa ser reescrita manualmente como `MERGE`, `UPDATE` com `JOIN`, ou
agregação. Isso é a causa mais comum de degradação de performance pós-migração quando ignorado.

```sql
-- Anti-padrão: cursor linha-a-linha (NUNCA reproduzir 1:1 no Databricks)
DECLARE @CustomerID INT, @TotalOrders INT;
DECLARE customer_cursor CURSOR FOR SELECT CustomerID FROM Sales.Customer;
OPEN customer_cursor;
FETCH NEXT FROM customer_cursor INTO @CustomerID;
WHILE @@FETCH_STATUS = 0
BEGIN
    SELECT @TotalOrders = COUNT(*) FROM Sales.SalesOrderHeader WHERE CustomerID = @CustomerID;
    UPDATE Sales.Customer SET TotalOrders = @TotalOrders WHERE CustomerID = @CustomerID;
    FETCH NEXT FROM customer_cursor INTO @CustomerID;
END;
CLOSE customer_cursor;
DEALLOCATE customer_cursor;
```

```sql
-- Databricks: substituição set-based via MERGE (mesmo resultado, uma única operação)
MERGE INTO migration_catalog.adventureworks_bronze.customer AS tgt
USING (
    SELECT CustomerId, COUNT(*) AS total_orders
    FROM migration_catalog.adventureworks_bronze.salesorderheader
    GROUP BY CustomerId
) AS src
ON tgt.CustomerId = src.CustomerId
WHEN MATCHED THEN
    UPDATE SET tgt.total_orders = src.total_orders;
```

Cite: `3.4 Lecture - SQL and Code Conversion.md`, seção "Cursor Patterns".

## 6. Requer Redesign (sem equivalente direto — decisão manual)

Lakebridge não transpila automaticamente os itens abaixo. Cada um exige avaliação manual e,
na maioria dos casos, reescrita da lógica (não apenas tradução sintática):

| Feature SQL Server | Abordagem de Migração |
|---|---|
| Dynamic SQL (`EXEC sp_executesql`) | Reescrever como Spark SQL parametrizado em notebook Python |
| CLR stored procedures | Reescrever em Python |
| Linked server queries | Lakehouse Federation, ou pré-copiar dados para Delta |
| Temp tables (`#temp`, `##global`) | `CREATE TEMP VIEW` ou CTE (`WITH`) |
| Table variables (`DECLARE @t TABLE`) | Temp views ou CTEs |
| `@@IDENTITY` / `SCOPE_IDENTITY()` | Sem equivalente exato — usar coluna `IDENTITY()` com default, ou sequence |
| `OUTPUT` clause em DML | Sem equivalente direto — capturar via Delta CDC (`table_changes()`) ou DML em duas etapas |
| `RAISERROR` / `THROW` | `RAISE` em SQL Scripting, ou exceptions em Python |
| `TRY...CATCH` | `EXCEPTION` handler em SQL Scripting; `try`/`except` em Python |
| `WAITFOR DELAY` | Agendamento via Lakeflow Jobs |
| Full-text search (`CONTAINS`, `FREETEXT`) | Databricks AI Functions, ou busca externa |
| `XACT_ABORT` / controle transacional | Lakeflow Declarative Pipelines cobre atomicidade nativamente; para batch, `try`/`except` em Python com Delta |
| `PRINT` / `SELECT` para debug | `RAISE INFO` em SQL Scripting, ou `print()` em Python |

Cite: `3.4 Lecture - SQL and Code Conversion.md`, seção "Features Requiring Manual Attention".

## 7. Checklist de Validação (pós-conversão)

- [ ] Namespaces atualizados (`database.schema` → `catalog.schema`)
- [ ] Tipos problemáticos revisados um a um (seção 1) — atenção especial a `TINYINT` (signed vs unsigned)
- [ ] `COLLATE`, filegroups e session settings removidos (seção 2.4)
- [ ] `IDENTITY`: `BY DEFAULT` na carga inicial; decisão sobre troca para `ALWAYS` documentada (seção 2.1)
- [ ] PKs com `RELY`; `UNIQUE` aplicado de fato via Lakeflow Declarative Pipelines expectations (seção 2.2)
- [ ] `CONVERT`/style codes mapeados para `DATE_FORMAT`/`TO_DATE`/`CAST` (seção 3.2)
- [ ] Cursors identificados e reescritos como set-based — nenhum 1:1 (seção 5)
- [ ] Stored procedures classificadas: SQL Scripting vs Python (seção 4)
- [ ] Lista "requer redesign" percorrida item a item (seção 6)
- [ ] Saída do Lakebridge revisada e validada contra dados de origem (nunca aceitar sem validação)
